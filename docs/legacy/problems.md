# Аудит legacy-прототипа `RDBMS-master`

## 1. Короткий вывод

`RDBMS-master` не подходит как основа новой СУБД. Его нужно хранить как исторический материал, но не развивать как текущую кодовую базу.

Правильное решение:

```text
код — не реанимировать;
идею — сохранить;
архитектуру — начать заново;
полезные термины — перенести в новую документацию.
```

## 2. Что это был за проект

Прототип состоял из маленького набора файлов:

```text
Cargo.toml
Cargo.lock
task.txt
src/main.rs
src/core.rs
```

По смыслу это был не storage engine, а черновой SQL dispatcher поверх in-memory структур:

```rust
Database {
    tables: Vec<Table>
}

Table {
    name: String,
    columns: Vec<Column>,
    rows: Vec<Row>
}
```

Для первого учебного опыта это нормально. Для новой цели — переносимого ядра СУБД — этого недостаточно.

## 3. Главная архитектурная ошибка

Проект начинался с функции вида:

```rust
pub fn sql_execute(&mut self, query: &str) -> Result<(), String>
```

и ручного разбора строк. То есть порядок был таким:

```text
SQL string → starts_with() → команды → когда-нибудь хранение
```

Для текущего RDBMS нужен обратный порядок:

```text
байты → страницы → WAL → recovery → catalog → heap table → transaction → SQL
```

Иначе SQL создаёт иллюзию готовой СУБД, хотя физического слоя ещё нет.

## 4. Чего не хватало

| Область | Состояние в legacy |
|---|---|
| Физический формат | отсутствует |
| Page layout | отсутствует |
| VFS/IO boundary | отсутствует |
| WAL | отсутствует |
| Recovery | отсутствует |
| Catalog | отсутствует как persistent layer |
| Transactions | отсутствуют |
| Индексы | отсутствуют |
| Parser | ручной `starts_with`/split |
| Executor | не отделён |
| Tests | отсутствуют |
| Extension API | отсутствует |
| Portability | не выделена |

## 5. Конкретные проблемы кода

### `CREATE` фактически не распознавался

В dispatcher были ветки команд, но определение типа запроса не покрывало весь набор команд. Из-за этого часть логики могла не достигаться.

### Ошибки терялись

`sql_execute` возвращал `Ok(())` даже тогда, когда внутренняя команда не выполнилась корректно. Для СУБД это плохой API: пользователь должен получить результат или ошибку.

### Большинство команд были `todo!()`

`SELECT`, `INSERT`, `DROP`, `DELETE`, `SHOW`, `USE` не были полноценными рабочими операциями.

### Таблица создавалась неустойчиво

Некоторые функции принимали `Database` по значению и возвращали изменённый объект, но вызывающий код не всегда применял результат обратно. Это ломало состояние.

### JSON snapshot не является storage engine

Сериализация Rust-структуры в JSON может быть debug export, но не заменяет:

- page format;
- WAL;
- recovery;
- compatibility policy;
- checksum;
- физические row ids.

## 6. Что было полезно

Legacy-прототип правильно нащупал предметные слова:

```text
Database
Table
Column
Row
DataType
Value
```

Эти термины можно сохранить. Но реализацию нужно строить заново.

## 7. Как legacy повлиял на текущий проект

Текущий RDBMS сохранил идею SQL-facing API, но перенёс фундамент ниже:

```text
rdbms_page
rdbms_vfs
rdbms_wal
rdbms_recovery
rdbms_catalog
rdbms_tx
rdbms_sql
rdbms_index
```

Теперь SQL layer не владеет хранением. Он вызывает transaction/storage API.

## 8. Практический вывод

При споре “добавить красивую SQL-команду или укрепить storage/recovery” для этого проекта обычно нужно выбирать второе.

Legacy уже показал, что SQL-first путь быстро становится тупиком.
