# problems.md — аудит бакалаврского черновика RDBMS-master

**Тема:** критика раннего проекта собственной СУБД.  
**Контекст:** проект был сделан как черновик уровня бакалавриата 4–5. Текущая целевая рамка — СУБД на Rust уровня 7: переносимое ядро, расширяемость, storage/recovery/transaction architecture, возможность работы минимум на Android, Linux и Windows.  
**Вердикт:** кодовую базу не воскрешать; идеи сохранить; архитектуру начать заново.

---

## 1. Короткий вердикт

Проект `RDBMS-master` **не подлежит воскрешению как основа будущей универсальной СУБД**.

Правильное решение:

```text
код — не реанимировать;
идею — сохранить;
архитектуру — перепроектировать;
часть терминов/намерений — перенести в новый ARCHITECTURE.md.
```

Проект имеет ценность как **археологический черновик / research spike**: он показывает раннюю интуицию о том, что СУБД состоит из базы, таблиц, колонок, строк, значений, типов данных и SQL-команд. Но он не является подходящим фундаментом для магистерского проекта уровня 7.

---

## 2. Что фактически представляет собой проект

Содержимое архива очень маленькое:

```text
Cargo.toml
Cargo.lock
task.txt
src/main.rs
src/core.rs
```

По смыслу это не СУБД, не storage engine и даже не законченная in-memory database. Это зачаток SQL-диспетчера поверх простых in-memory структур.

Основные сущности:

```rust
Database {
    tables: Vec<Table>
}

Table {
    name: String,
    columns: Vec<Column>,
    rows: Vec<Row>
}

Column {
    name: String,
    data_type: DataType
}

Row {
    values: Vec<Value>
}
```

Это нормальная первая бакалаврская модель: “база содержит таблицы, таблицы содержат строки, строки содержат значения”. Но это ещё не архитектура СУБД.

---

## 3. Главная архитектурная проблема

Проект начинается с SQL-команд и диспетчера запросов:

```rust
pub fn sql_execute(&mut self, query: &str) -> Result<(), String>
```

и логики вида:

```rust
sql_distribute(self, String::from(query));
```

Но для зрелой СУБД правильная последовательность другая:

```text
байты → страницы → WAL → каталог → таблица → транзакция → индекс → запрос → расширение → переносимость
```

Текущий черновик идёт почти в обратную сторону:

```text
SQL-строка → starts_with() → CREATE/SELECT/INSERT/... → потом когда-нибудь хранение
```

Это не косметическая проблема, а архитектурная инверсия. Видимый SQL shell создаёт иллюзию прогресса, но не строит СУБД как систему гарантий.

---

## 4. Критика по критериям зрелой СУБД

| Критерий зрелой СУБД | Состояние в черновике | Оценка |
|---|---|---:|
| Stable physical format | отсутствует; есть попытка JSON-сериализации всей структуры | 0/5 |
| Page layout / slotted pages | отсутствует | 0/5 |
| VFS / IO-абстракция | отсутствует; напрямую `OpenOptions` | 0/5 |
| WAL / recovery | отсутствует | 0/5 |
| Catalog | отсутствует; метаданные живут как Rust-поля | 0/5 |
| Transactions | отсутствуют | 0/5 |
| Индексы | отсутствуют | 0/5 |
| Query parser | отсутствует; только `starts_with()` и `split_terminator(" ")` | 1/5 |
| Query planner/executor | отсутствует | 0/5 |
| Типовая система | есть зачаток `Text`, `Integer`, `Double` | 1/5 |
| Persistence | функция `create_db_file`, но она не встроена в execution path | 1/5 |
| Error model | есть `RDBMS_E`, но он не интегрирован в API | 1/5 |
| Tests | отсутствуют | 0/5 |
| Extension API | отсутствует | 0/5 |
| Android/Linux/Windows portability | отсутствует как архитектурный слой | 0/5 |

Суммарно: это не “недописанная СУБД”, а понятийный скелет раннего учебного прототипа.

## 5. Конкретные дефекты кода

### 5.1. `CREATE` фактически не распознаётся

В диспетчере есть ветка под `CREATE`, но в функции определения типа запроса нет проверки на `CREATE`:

```rust
fn get_query_type(query: String) -> QueryType {
    match query {
        q if q.starts_with("SELECT") => QueryType::SELECT,
        q if q.starts_with("SHOW") => QueryType::SHOW,
        q if q.starts_with("USE") => QueryType::USE,
        q if q.starts_with("DROP") => QueryType::DROP,
        q if q.starts_with("DELETE") => QueryType::DELETE,
        q if q.starts_with("INSERT") => QueryType::INSERT,
        _ => QueryType::ERROR
    }
}
```

Следствие: даже наиболее проработанная команда не достигает своей ветки выполнения.

### 5.2. `sql_execute` игнорирует результат выполнения

```rust
sql_distribute(self, String::from(query));
Ok(())
```

Любая ошибка теряется. Любой `SqlResult` теряется. API сообщает `Ok(())`, даже если запрос не распознан или не выполнен.

Это ломает базовый контракт СУБД: команда должна возвращать результат, ошибку или хотя бы корректное описание эффекта.

### 5.3. Большинство команд оставлены как `todo!()`

В `task.txt` состояние проекта фактически такое:

```text
+ распределитель запросов
* sql_create
- sql_select
- sql_show
- sql_drop
- sql_remove
- sql_insert
- sql_use
- error_query
```

В коде это соответствует реальности: `DELETE`, `DROP`, `INSERT`, `SELECT`, `SHOW`, `USE` не реализованы.

### 5.4. Таблица создаётся не в текущей базе

Функция создания таблицы принимает `Database` по значению:

```rust
fn create_table(name: String, mut current_db: Database) -> SqlResult
```

Она мутирует переданную базу и возвращает новую базу в `SqlResult::DB`, но вызывающий код не применяет результат обратно к `self`.

Следствие: даже если команда создания таблицы была бы достигнута, состояние основной БД не обновлялось бы надёжным образом.

### 5.5. “Файл БД” — это JSON-снимок Rust-структуры

```rust
let ser_db = serde_json::to_string_pretty(db).unwrap();
```

Для учебного дампа это допустимо. Для СУБД — нет.

```text
serde_json снимок ≠ storage engine
serde_json снимок ≠ page format
serde_json снимок ≠ WAL
serde_json снимок ≠ crash recovery
serde_json снимок ≠ совместимый бинарный формат
```

JSON можно использовать как debug export, но не как основной формат базы данных.

## 6. Что в проекте всё же ценно

### 6.1. Правильно нащупаны базовые доменные сущности

```text
Database
Table
Column
Row
DataType
Value
```

Это не архитектура СУБД, но нормальная первая модель предметной области.

### 6.2. Логика отделена от `main.rs`

`main.rs` почти пустой, а логика вынесена в `core.rs`. Намерение правильное: СУБД не должна жить внутри CLI.

В новом проекте это нужно развить до workspace-структуры:

```text
crates/db_core
crates/db_vfs
crates/db_page
crates/db_wal
crates/db_catalog
crates/db_sql
crates/db_cli
crates/db_ext_abi
```

### 6.3. Есть первая попытка результата исполнения

```rust
pub enum SqlResult {
    DB(Database),
    Rows(Vec<Row>),
    Columns(Vec<Column>),
    Table(Table),
    Error(RDBMS_E)
}
```

Форма наивная, но интуиция верная: разные запросы возвращают разные типы результата.

В новом проекте это должно стать чем-то вроде:

```rust
enum ExecResult {
    StatementComplete { rows_affected: u64 },
    Query { columns: Vec<ColumnInfo>, rows: RowStream },
    Explain { plan: PlanDump },
}
```

### 6.4. Есть попытка различить RAM-БД и файловую БД

```text
DBRAM
DB
```

Это хорошая интуиция. В зрелой архитектуре это должно стать не SQL-командой, а режимом открытия:

```rust
Database::open_in_memory()
Database::open(path, options)
```

## 7. Почему проект не стоит чинить напрямую

Проблема не в том, что мало реализовано. Мало реализовано — нормально для раннего прототипа.

Проблема в том, что точка старта выбрана не та.

Если продолжать текущий код, придётся постепенно приклеивать:

```text
парсер к строковому диспетчеру;
хранение к Vec<Table>;
ошибки к Result<(), String>;
файлы к serde_json;
транзакции к структурам, которые не знают LSN;
индексы к строкам, которые не имеют физического адреса;
плагины к ядру, где ещё нет стабильных внутренних контрактов.
```

Такой проект превратится в архитектурный комок. Его всё равно придётся переписывать.

## 8. Как начать заново правильно

Новый проект не должен начинаться с SQL shell.

Первый этап должен быть не про `SELECT`, а про физическую основу:

```text
создать файл БД;
записать страницу;
прочитать страницу;
проверить checksum;
переоткрыть файл;
обнаружить повреждённую страницу.
```

Минимальный набор документов до активного кодинга:

```text
ARCHITECTURE.md
NON_GOALS.md
FORMAT.md
WAL.md
RECOVERY.md
EXTENSION_ABI.md
ROADMAP.md
```

Рекомендуемый каркас:


## 9. Что перенести из старого проекта

Перенести:

```text
1. Имена базовых понятий: Database/Table/Column/Row/Value.
2. Идею SQL-facing API, но не реализацию.
3. Различение in-memory и persistent режима.
4. Список команд из task.txt как исторический backlog, но не как roadmap.
5. Сам факт желания писать на Rust.
```

Не переносить:

```text
1. src/core.rs как основу.
2. starts_with-парсер.
3. JSON как формат БД.
4. Vec<Table> как центральное хранилище.
5. Result<(), String> для исполнения запросов.
6. CREATE/DBRAM/DB как SQL-синтаксис.
7. Монолитный core.rs.
```

## 10. Итоговый диагноз

Бакалаврский черновик отвечает на вопрос:

```text
“Как мне представить БД в памяти и начать принимать текстовые команды?”
```

Текущая цель уровня 7 требует ответа на другой вопрос:

```text
“Какие инварианты хранения, восстановления, транзакций, каталога, исполнения запросов и расширений должно гарантировать переносимое СУБД-ядро?”
```

Это разные задачи.

```text
RDBMS-master — не предок будущей СУБД.
RDBMS-master — эмбриональная заметка о том, что тема СУБД была интересна уже тогда.
```

---

## 11. Решение на будущее

Начать новый проект с нуля.

Старый проект сохранить как:

```text
docs/legacy/RDBMS-master/
docs/legacy/problems.md
```

Рекомендуемая запись в `docs/legacy/README.md`:

```text
Этот код не является основой новой архитектуры.
Он сохранён как бакалаврский прототип уровня 4–5.

Ценность:
- ранняя модель сущностей;
- список желаемых SQL-команд;
- фиксация интереса к теме СУБД;
- исходная точка эволюции мышления.

Причина отказа от прямого продолжения:
- отсутствие storage/recovery/catalog/transaction architecture;
- отсутствие устойчивого physical format;
- неверный порядок построения: SQL раньше хранения;
- монолитность;
- отсутствие тестовой и расширяемой основы.
```
